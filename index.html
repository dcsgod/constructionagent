At L&T, operational signals arrive through many unstructured channels simultaneously. The AI system must listen to all of them and decide what is actionable.

Vendor registration docs, delivery challans, compliance certificates.

Why this matters independently: This layer is separate because each source has its own auth, format, and rate limit. WhatsApp uses webhooks (push); ERP uses polling (pull); PDFs use OCR. The ingestion logic per source can be updated without touching AI logic.

Layer 2 — Data Ingestion & Storage
NORMALISE, ROUTE & PERSIST
＋

Raw signals are noisy. This layer cleans, routes, and stores them so the AI layer can work with structured inputs. Think of it as the nervous system — it converts impulses into usable signals.

A
Azure Event Hub catches the WhatsApp webhook
Rajesh's message arrives as a JSON event. Event Hub buffers it and fans out to two consumers: the ETL pipeline and the AI stream processor. Guarantees no message is lost even under spike load.
Event Hub · Streaming Consumer Groups JSON payload
B
Azure Data Factory ETL — normalise & enrich
The pipeline extracts metadata: sender ID → mapped to project code MUM-042, timestamp, source channel. It also triggers a pull from SAP ERP: "What is the current TMT stock level for MUM-042?" Result: 80 MT on hand. Deficit = 420 MT.
ADF Pipeline SAP REST Connector Schema mapping
C
Blob Storage — raw message archived
Original WhatsApp message, voice note (if any), and any attachments are stored in Blob with a unique event ID. This is the immutable record — used for audit trail and model retraining later.
Azure Blob Immutable archive Event ID linking
D
Azure SQL DB — structured procurement record created
A new row is inserted: procurement_requests table. Fields: project_id, material_type = "TMT Steel", quantity = 420 MT (adjusted), urgency = HIGH, deadline = 7 days, status = OPEN.
Azure SQL Structured schema FK to vendor master
E
Cosmos DB — operational state initialised
A document is created in Cosmos DB with the full context object. This is the "working memory" the LangGraph agent will read and write to as it progresses through the workflow. Accessible in < 10ms.

🧠
Layer 3 — AI Intelligence Layer
WHERE THE SYSTEM THINKS, RANKS & DECIDES
＋

This is the brain. Five specialised AI components fire in sequence, each solving one cognitive sub-problem. Together they go from "what does Rajesh need?" to "here is the ranked vendor list with a confidence score."

1
Azure OpenAI — Intent Extraction (LLM Understanding)
GPT-4o receives the message + context. Prompt: "Extract: material, quantity, unit, urgency, project constraints from this message. Return JSON."

Output: {"material":"TMT Steel Bar","grade":"Fe500","qty":420,"unit":"MT","urgency":"HIGH","deadline_days":7,"project":"MUM-042"}
GPT-4o Structured output JSON extraction
2
Azure AI Search — Vendor RAG Lookup
Vector search against the vendor knowledge base (10,000+ vendor profiles, past performance PDFs, compliance certs). Query: "TMT Fe500 Mumbai 420MT 7-day delivery." Returns top 8 matching vendors with semantic similarity scores.

Why RAG over SQL JOIN? Because vendor capability is described in unstructured text — PDFs, emails. A simple SQL filter would miss a vendor who says "we handle structural steel projects across Maharashtra."
Vector embeddings Semantic search Hybrid BM25 + cosine
3
Azure Machine Learning — Vendor Score Prediction
A trained gradient boosting model (XGBoost) scores each of the 8 shortlisted vendors on:
• Delivery probability within 7 days (0–1)
• Price competitiveness index
• Quality score (from past inspection reports)
• Financial health (payment delay risk)

Features trained on 3 years of L&T procurement history (50,000+ POs).
XGBoost Gradient Boosting ML endpoint (REST)
4
Azure Databricks — Feature Engineering
Runs a real-time Spark job to compute dynamic features that the static ML model can't do alone:
• How many active L&T orders does each vendor currently have? (capacity check)
• Is there a monsoon disruption affecting delivery routes?
• Current steel price index (commodity API)

These enriched features are passed back to the ML model for final scoring.
Databricks Spark Streaming Feature Store
5
LangGraph Orchestrator — Agent Decision Loop
The agent receives the scored vendor list and runs a multi-step decision graph:

Node 1 — Check Policy: Is the top vendor on approved vendor list? Is value under ₹50L auto-approve threshold?
Node 2 — Conflict Check: Does this vendor have an open dispute or blacklist flag?
Node 3 — Route Decision: If all checks pass → AUTO-ASSIGN. Else → HUMAN REVIEW queue.

Result: Vendor "Tata Steel Distributors Pvt Ltd" selected. Score: 0.91. Value: ₹38.2L. AUTO-ASSIGN path triggered.
LangGraph State machine Tool calls Policy engine
Layer 3 is independent because: You can swap XGBoost for a neural net, or replace GPT-4o with Gemini — without touching storage or execution layers. Each component exposes a REST endpoint. The orchestrator only cares about inputs and outputs.

Human Approval & Guardrails (right side of diagram): When a decision routes to human approval, the LangGraph agent pauses at a checkpoint node and sends a structured approval request to the manager's app. The manager sees: AI recommendation, confidence score, top 3 alternatives, and risk flags. They can Approve / Reject / Modify. The agent resumes from the checkpoint.

Layer 5 — Monitoring & Governance
ALWAYS WATCHING, ALWAYS LEARNING
＋

This layer is always running. It tracks every action taken, detects anomalies, enforces compliance, and feeds data back to improve the ML models. It's not optional — it's what makes the system trustworthy over time.

📊
Azure Monitor
Tracks pipeline latency, error rates, API call counts. Fires alert if vendor assignment takes >2 minutes (SLA breach).
💡
Application Insights
End-to-end distributed tracing. Every step from WhatsApp message to PO creation gets a span ID — full debug trail.
👁️
Microsoft Purview
Data lineage: shows which source data influenced which AI decision. Required for audits ("why was vendor X chosen?").
🔐
Key Vault
All secrets (API keys, DB passwords, vendor portal credentials) are stored here — never hardcoded. Rotated automatically.

Part 4
3-Phase Execution Plan
Phase 1 · Months 1–4
MVP — Rule-Based + Simple ML
Deploy Layer 1 & 2 only. Manually ingest WhatsApp requests. Rule-based vendor shortlisting (approved vendor list + material type filter). Simple scoring by past delivery rate from SQL history. Team: 1 data engineer, 1 ML engineer, 1 PM. Infra: Azure Data Factory + SQL DB only. Goal: prove 30% faster vendor shortlisting vs manual.
Phase 2 · Months 5–9
Learning System — Full ML + RAG
Add Layer 3 (OpenAI + AI Search + XGBoost model). Train on 2 years of historical PO data. Enable automated email RFQ via Logic Apps. Build procurement dashboard. Team adds: NLP engineer, MLOps engineer, Azure architect. Goal: model achieves >80% correct vendor recommendation. Human reviews all decisions but AI does the legwork.
Phase 3 · Months 10–15
Autonomous System — Full Agentic Orchestration
Deploy LangGraph orchestrator. Enable auto-PO for sub-₹50L transactions. WhatsApp → PO in under 5 minutes. Full Monitoring (Layer 5). Weekly model retraining loop. Team adds: AI safety reviewer, compliance officer sign-off. Goal: 60% of procurements fully automated. 40% require human review but AI drafts everything.
Part 5
Failure Scenarios
⚠️ Model Picks Biased Vendor
The ML model was trained on 3 years of data where large Mumbai vendors were always selected — it systematically scores smaller vendors lower, even when they're cheaper and equally capable.
Mitigation
Fairness audit on model outputs every quarter. Monitor vendor diversity metrics in Application Insights. Introduce price-normalised scoring. Human review flag if 1 vendor gets >40% of orders for a project.
⚠️ LLM Misreads Ambiguous Message
Rajesh writes "need steel for next week — same as last time." GPT-4o hallucinates the grade/quantity from context. Wrong PO is raised for Fe415 instead of Fe500, causing structural non-compliance.
Mitigation
All LLM extractions include a confidence threshold. If any field has <85% confidence, system sends a clarification WhatsApp to Rajesh before proceeding. Critical spec fields (material grade) always require explicit confirmation.
⚠️ Vendor Portal API Goes Down
Tata Steel Distributors' vendor API is unavailable. The agent can't place the order. Meanwhile, Rajesh thinks it's done. Steel doesn't arrive. Foundation work is delayed by 3 days, costing ₹12L in contractor penalties.
Mitigation
Circuit breaker pattern on all vendor API calls. If API fails after 3 retries, fallback to email order + human notification. Azure Monitor triggers alert. SLA countdown pauses and stakeholder is notified within 5 minutes of failure.
